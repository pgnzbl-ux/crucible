# 漏洞评分（CVSS 3.1）—— 客观、分场景、不激进

> 判定 `confirmed` / `partial` 时**强制执行**本规范后再产出 `cvss`。
> 核心原则：**verdict 与 severity 分离**。verdict 由 HTTP 证据定；severity 必须由 CVSS 3.1 算出，禁止拍脑袋写"高危/中危"。
> 误报 / 未复现 / code_reachable / code_smell 不评分（schema 也禁止交 `cvss`）。

## 1. 输出格式（强制）

`cvss` 对象必须含完整向量 + 分数 + 等级，禁止只有定性词：

```
vector: AV:N/AC:L/PR:N/UI:N/C:H/I:H/A:H
base_score: 9.8
severity: Critical
```

## 2. 分场景评分（利用性/影响依赖部署实况时强制）

同一漏洞在不同部署形态下分数可能完全不同，**在 `evidence`/叙述里拆场景**，不允许只给一个分数：

| 场景 | 说明 | 向量示例 | 分数 |
|------|------|-----------|------|
| A. 默认凭据未改 | README/文档公开凭据 | `AV:N/AC:L/PR:N/UI:N/C:H/I:H/A:H` | 9.8 Critical |
| B. 已改非默认密码 | 纯暴力破解，概率性利用 | `AV:N/AC:H/PR:N/UI:N/C:L/I:L/A:L` | 5.3~6.5 Medium |
| C. 强随机密码 | 仅纵深防御缺失 | — | Low / code_smell |

本节点**实际验证了哪个场景**，`cvss` 就按该场景计——禁止默认取最坏场景（那是 report 叙述里给报送的参考信息）。

## 3. 反激进护栏（防止高估，强制）

**分数 = 可利用的确定性 × 影响**，两者缺一不可。

### 3.1 概率性利用 → 默认 Medium 上限

利用需要"猜中/碰运气"（暴力破解、口令猜测、弱密钥穷举）：默认上限 Medium（6.5），除非存在**可验证的确定性条件**才可上调：公开默认凭据未改 / 已知弱密码且能证明该账户在用 / 凭据泄漏且可验证可登录。
**影响大 ≠ 分数高**：管理员账户失守影响很大，但只能靠猜密码就是概率性利用。

### 3.2 弱点 ≠ 漏洞

仅"缺防护机制"而无确定性利用路径（无限速/无锁定/无 MFA）：定级不高于 Medium，倾向 `code_smell`。

### 3.3 未证实的能力不得计入 Impact

C/I/A 只按**已验证的、攻击者可观察的**后果计。SSRF 未外泄敏感数据 → `partial` + C:L 起步；IDOR 仅非敏感字段 → `partial` + Impact 打折。"理论上可能读到"不算。

### 3.4 权限/前置如实计分

需认证 → 按实际权限计 PR，不得默认 PR:N；复杂前置 → AC:H；本机绑定端点 → AV:L/P，不得 AV:N。

### 3.5 不确定参数取保守值

密码强度未知按 Medium 场景，不按"默认凭据"最坏场景；影响不明取已证实最小影响；多解列各场景、主定级取验证场景。

### 3.6 常见误评对照

| 类型 | 常见误评 | 正确做法 |
|------|----------|----------|
| 登录端点无速率限制 | High 8.x | Medium 5.3~6.5 上限；默认凭据未改才 Critical |
| 纯暴力破解（已改密） | C:H/I:H/A:H 直算 | Impact 打折 + AC:H → 5.3~6.5 |
| 仅信息泄露（版本/堆栈） | Medium | Low，通常归 code_smell |
| SSRF 无外泄 | High | partial + C:L，Medium 上限 |
| 需登录的高影响功能 | 按匿名计 | PR:H 如实降分 |
| 内网/本机绑定 | AV:N | AV:L |

## 4. 交卷自检（任一为"是"则回到护栏重算）

1. 分数是否建立在"攻击者必成功"的假设上，而实际需要猜/试？
2. 是否把未验证的理论影响算进了 C/I/A？
3. 是否默认了最坏部署场景，而不是本节点验证过的场景？
