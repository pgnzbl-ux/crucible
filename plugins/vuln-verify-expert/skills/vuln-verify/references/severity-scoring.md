# 漏洞评分（CVSS 3.1）—— 客观、分场景、不激进

> 本文件是 vuln-verify 的强制评分流程（Phase 5.5）的操作规范。
> **核心原则：verdict（是否漏洞）与 severity（严重等级）分离。verdict 由 Phase 3 的证据定；severity 必须由 CVSS 3.1 算出来，禁止拍脑袋写"高危/中危"。**

## 0. 评分时机

- **必做**：每个"已确认 / 部分确认"的漏洞，在 Phase 5 写报告前完成评分；报告必须含评分小节（§2.1 或报告模板对应位置）。
- 误报 / 未复现 / Quick-Stop 无需评分（但可在结论里注明"若成立，预估场景与等级"供参考）。

## 1. 评分输出格式（强制）

报告必须给出**完整向量 + 分数 + 等级**，禁止只写"高危"这类定性词：

```
CVSS 3.1 向量：AV:N/AC:L/PR:N/UI:N/C:H/I:H/A:H
Base Score：9.8    等级：Critical
```

## 2. 分场景评分（强制，当利用性/影响依赖部署实况时）

同一漏洞在不同部署形态下分数可能完全不同，**必须拆场景列表**，不允许只给一个分数：

| 场景 | 说明（触发条件） | CVSS 向量 | 分数 |
|------|------------------|-----------|------|
| A. 默认凭据未改 | README/文档公开凭据，无需猜测 | `AV:N/AC:L/PR:N/UI:N/C:H/I:H/A:H` | 9.8 Critical |
| B. 已改非默认密码 | 纯暴力破解，概率性利用 | `AV:N/AC:H/PR:N/UI:N/C:L/I:L/A:L` 或 `C:L/I:L/A:N` | 5.3 ~ 6.5 Medium |
| C. 强随机密码 | 破解不可行，仅纵深防御缺失 | — | Low / 纵深防御建议 |

- 报告顶部"危害等级"行必须引用评分小节并注明"按部署实况选择对应等级"，禁止默认取最坏场景。
- 本报告实际验证了哪个场景，就**以该场景为主要定级**，其它场景作为报送参考。

## 3. 反激进护栏（防止高估，强制）

以下规则用于对抗"影响大就评高分"的直觉。**分数 = 可利用的确定性 × 影响**，两者缺一不可。

### 3.1 概率性利用 → 默认 Medium 上限

利用需要"猜中/碰运气/试错"才成立（暴力破解、口令猜测、弱密钥穷举、依赖随机性）：
- **默认上限 Medium（6.5）**，除非存在可验证的确定性条件才可上调。
- 可上调的确定性条件（至少其一，且要在报告里写明依据）：
  - 公开的默认凭据未修改（README/文档/源码硬编码）；
  - 已知的弱密码/常见密码且能证明该账户用此密码；
  - 凭据已泄漏（如历史数据泄露）且可验证可登录。
- **影响大 ≠ 分数高**：超级管理员账户失守影响很大，但若只能靠猜密码，只能按概率性利用处理。

### 3.2 弱点 ≠ 漏洞

仅"缺少防护机制"而无确定性可利用路径（无限速、无锁定、无 MFA、无审计日志、纵深防御缺失）：
- 定级 **不高于 Medium**；
- 倾向标注为"纵深防御建议 / CODE SMELL"，并说明叠加什么条件会升级。

### 3.3 未证实的能力不得计入 Impact

- 影响（C/I/A）只按**验证过的、攻击者可观察的**后果计分；"理论上可能读到的数据"未验证不得算 High。
- SSRF 未外泄敏感数据 → 部分确认 + Impact 打折（C:L 起步）。
- IDOR 仅影响非敏感字段 → 部分确认 + Impact 打折。

### 3.4 权限/前置条件如实计分

- 需要认证才能利用 → 按实际所需权限计 PR（High 权限会显著降分，如实计算，不得默认 PR:N）。
- 需要特定业务前置 / 复杂条件 → 按 AC:H 或分场景说明。
- 本地才能访问的端点（127.0.0.1 绑定）→ AV:L 或 AV:P，不得按 AV:N。

### 3.5 不确定参数取保守值

- 密码强度未知 → 按 Medium 场景说明，不按最坏场景（默认凭据）计。
- 影响范围不明 → 取已证实的最小影响。
- 多解时在报告里列出各场景分数，主定级取验证场景。

### 3.6 常见误评对照表

| 类型 | 常见误评（激进） | 正确做法 |
|------|------------------|----------|
| 登录端点无速率限制/无锁定 | High（8.x） | Medium（5.3~6.5）上限；默认凭据未改才是 Critical |
| 纯暴力破解（已改密） | 按 C:H/I:H/A:H 直算 | Impact 打折，AC:H，5.3~6.5 Medium |
| 仅信息泄露（版本号/堆栈） | Medium | Low，通常不单独报送 |
| SSRF 无外泄 | High | 部分确认 + C:L，Medium 上限 |
| 需要登录的高影响功能 | 按匿名影响计 | 按 PR:H 如实计算，通常降至 Medium |
| 内网/本机绑定端点 | AV:N | AV:L，如实降分 |

## 4. 评分依据与复核

- 基准：CVSS v3.1（FIRST 官方公式）。**必须能写出完整向量**，不允许只报分数。
- 参考业界 CNA 惯例（如对"需猜中密码"按 AC:H + Impact 打折）时，在报告"危害等级"小节注明依据，便于复核。
- 评分后自问三个问题（任一为"是"则回到护栏 3.x 检查）：
  1. 这个分数是否建立在"攻击者一定能成功利用"的假设上，而实际需要猜/试？
  2. 是否把未验证的"理论影响"算进了 C/I/A？
  3. 是否默认了最坏部署场景，而不是验证过的场景？

## 5. 报告落点

- 报告新增/确保小节：`2.1 CVSS 3.1 评分（分场景）`（或模板指定位置），含：完整向量、Base Score、等级、各场景说明、"主定级 = 本报告验证场景"声明。
- 报告顶部"危害等级"行引用该小节。
- "报送判定"必须附定级指引：按目标部署实况选场景，避免高估（报送被驳回）或低估（风险被忽视）。
