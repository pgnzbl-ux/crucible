# 不污染本地环境

贯穿全程的约束：**宿主机只需要 Docker，其它一切装进容器**。目标是环境跑完能彻底清除、不留残留，也不影响宿主机已有的软件与端口。

## 核心原则

1. **不往宿主机装运行时**：不装 JDK/Node/Python/Go、不装 MySQL/Redis 等中间件到宿主机。全部用容器。
2. **不全局改宿主机**：不改宿主机 hosts、系统服务、全局环境变量、PATH。
3. **依赖装在容器内**：`npm install`/`mvn`/`pip install` 都发生在镜像构建期或容器内，不在宿主机跑。
4. **数据留在可清理的位置**：用命名卷或项目内相对目录，不往宿主机任意路径写。

## 具体做法

### 用命名卷或项目内目录持久化

```yaml
volumes:
  db_data:            # 命名卷，docker compose down -v 一并清除
services:
  db:
    volumes:
      - db_data:/var/lib/mysql
  app:
    volumes:
      - ./.run-env/uploads:/app/upload   # 项目内相对目录，清理时删目录即可
```

避免 `/absolute/host/path:/...` 这类散落到宿主机各处的绑定挂载。

### 端口映射避让

只把必要端口映射到宿主机，且避开常用端口，减少与宿主机既有服务冲突（见排障文档端口冲突处理）。数据库等内部服务尽量**不对宿主机暴露端口**，只在 compose 网络内互连。

### 网络隔离

用 compose 默认或具名网络，让服务间通过 service 名通信，不依赖宿主机网络。

### 构建产物集中存放

调试过程中生成的 Dockerfile、compose、临时脚本尽量集中在项目内（可放 `.run-env/` 子目录），便于最后统一保留或清理，不散落到宿主机其它地方。

## 清理方式（写入 RUN_ENV.md 告知用户）

```bash
# 停止并移除容器、网络（保留数据卷）
docker compose down

# 连同数据卷一起清除（彻底清数据）
docker compose down -v

# 删除本次构建的镜像（可选，彻底不留镜像）
docker compose down --rmi local

# 项目内数据目录
rm -rf .run-env/
```

停止/清理属可逆的环境操作，一般无需逐次确认；但 `down -v` 会删除数据卷，若其中有用户已产生的重要数据，先与用户确认。

## 例外与告知

- 若某项目确实无法完全容器化（如需要宿主机特定硬件/驱动、GPU 直通、特殊内核模块），如实告知用户需要在宿主机做的最小改动，并说明影响，由用户决定。
- 需要拉取大镜像或占用较多磁盘时，简要提示用户。
